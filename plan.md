# 🚀 План параллельной работы над проектом «Базы данных»

## 1. Почему мы не сломаем Git при одновременной работе
В структуре репозитория у каждой роли свои отдельные файлы[cite: 1]. Пока каждый редактирует и добавляет в коммит (`git add <файл>`) только свои файлы, конфликтов в Git не возникнет:

* 👤 **Аналитик** работает только с файлами:
  * `docs/analysis/data_map.md` (Описание предметной области и карта данных)[cite: 1]
  * `docs/analysis/access_matrix.md` (Матрица доступа и требования к защите)[cite: 1]
  * `docs/diagrams/er_diagram.png` (ER-диаграмма)[cite: 1]
  * `sql/schema.sql` (DDL-скрипт: таблицы, ограничения, индексы)[cite: 1]
  * `sql/queries.sql` (Аналитические запросы, VIEW и MATERIALIZED VIEW)[cite: 1]
* 👤 **Администратор** работает только с файлами:
  * `docs/analysis/data_flow.png` (Схема потоков данных)[cite: 1]
  * `sql/triggers_functions.sql` (Функции, процедуры, триггеры и статистика)[cite: 1]
  * `sql/roles.sql` (DCL-скрипты: роли, GRANT/REVOKE)[cite: 1]
* 👤 **Разработчик** работает только с файлами:
  * `sql/seed.sql` (Тестовые данные или скрипт генерации на 1M+ строк)[cite: 1]
  * `python/db_access.py` (Скрипт подключения и выгрузки данных)[cite: 1]
  * `README.md` (Описание проекта, результаты EXPLAIN ANALYZE)[cite: 1]

## 3. Шпаргалка: как пушить свою задачу в Git, чтобы ничего не сломать

Никогда не пушим напрямую в `main` и не используем `git add .` (чтобы случайно не запушить тяжелый CSV-датасет). Для каждой задачи выполняем 5 шагов в терминале:

```bash
# 1. Переключаемся на main и скачиваем свежие изменения
git checkout main
git pull origin main

# 2. Создаем отдельную ветку под свою задачу
git checkout -b feat/название-задачи

# 3. Добавляем ТОЛЬКО свой файл
git add путь/к/твоему_файлу

# 4. Делаем коммит
git commit -m "feat: краткое описание того, что сделано"

# 5. Отправляем ветку в GitHub
git push -u origin feat/название-задачи
